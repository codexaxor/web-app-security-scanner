## API changes

| Method | Path | Example request / response |
| --- | --- | --- |
| GET | `/api/v1/dashboard/summary` | → `{bands:{critical,high,medium,low}, total, types:[{type,count}], scanHealth:{...}, recentScans:[...]}` |
| GET | `/api/v1/issue-groups?view=focus\|all&band=&repositoryId=&type=&includeInactive=&page=&size=` | paginated groups; each row has `repositoryPath`, `severityScore`, `openCount/ignoredCount/solvedCount` |
| GET | `/api/v1/issue-groups/summary?view=&repositoryId=&type=&includeInactive=` | → `{bands:{...}, total, newFindings, solved, autoIgnored}` (7-day buckets) |
| GET | `/api/v1/issue-groups/{id}` | one group for the side-panel header (404 if outside workspace) |
| GET | `/api/v1/issue-groups/{id}/sub-issues?page=&size=` | sub-issues with holding-rule fields (`ignoreRuleId/ruleScope/ruleReason/ruleCreatedBy`) |
| GET | `/api/v1/sub-issues/{id}/events?page=&size=` | one sub-issue's status history, newest first |
| GET | `/api/v1/scans?page=&size=` | workspace-wide scan list |
| GET | `/api/v1/scans/{id}/warnings` | scan warnings for the side drawer |
| PATCH | `/api/v1/repositories/{id}` | `{sensitivity?,includeDevDeps?,active?}` → updated `RepositoryView`; sensitivity triggers immediate re-score (D-070) |

(The EPSS toggle `GET/PUT /api/v1/workspace/settings` is M7 and unchanged; M8 only consumes it.)

## Known gaps / TODOs

- **Stale `issue_group.severity_score` on all-ignored groups (investigate; report evidence only, NOT fixed in M8).**
  The side-panel header reads the `severity_score` column raw (`SubIssuePanel.tsx:52` → `IssueService.getGroup`
  → `IssueGroupView.of` → `IssueGroup.getSeverityScore()`), and the UI's `SeverityPill` correctly renders a
  neutral "—" for a *null* score (D-068). `GroupRollupService` defines the column as **max over the
  currently-OPEN sub-issues** (null when none are open), so a correctly-recomputed all-ignored group is null.
  But the invariant "all-ignored ⇒ null" is re-asserted **only by a scan-time reconcile of that group**
  (`ReconcileService` → `GroupRollupService.recompute`): every API-time maintenance path recomputes **only groups
  that still have an open sub-issue** — the re-score job builds `touchedGroups` from OPEN subs
  (`ReScoreService.rescoreWorkspace`, lines 139/155–158), the EPSS sweep recomputes only groups `touched` by that
  sweep (`WorkspaceSettingsService.autoIgnoreLowEpss`/`setEpssAutoIgnore`, lines 80–85/104–116), and manual
  triage only `touched` groups (`TriageService.recomputeGroups`, 198–205). So between scans a group that reaches
  all-ignored can retain a stale non-null band — the max over whatever was open at its last recompute.
  **Observed:** org.postgresql:postgresql (core-keycloak) header showed "Medium 65" while both its findings were
  ignored (Medium 65 + High 82) — the stale value is the earlier open-set max (65), the High-82 sibling having
  been ignored before that recompute. **Classification:** display/rollup-staleness, not data integrity — sub-issue
  statuses and the Feed band totals are correct; only the panel header's band is stale. Suggested fix direction
  (M8.5): have the API-time paths also recompute a group that has just become all-ignored (null it), or re-derive
  the header band from the sub-issues at read time. Recorded in the deferred register.
