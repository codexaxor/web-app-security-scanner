## Key decisions (D-104)

- **No SHA bump** — `check_id` is a fingerprint input; a bump would churn every SAST finding. Only rule YAML is
  baked (never the packs' `*.test.yaml` / test sources).
- **Noise control, NEW packs only.** Denying/retiring an *existing* pack rule would make reconcile "solve" its
  live findings (reads as fixed) — out of scope (`rule retired ≠ fixed`, deferred). Deny-list = 20 full
  `check_id`s; category exclusions = **122** (`best-practice`/`compatibility`/`correctness`/`maintainability`/
  `performance`) via a committed, diff-gated generated list; the one `caching` rule is kept.
- **Locale:** `LANG=C.UTF-8 LC_ALL=C.UTF-8` for every `opengrep` call.
- **Taint:** `--taint-intrafile` changes no fingerprint input (rule_id, file_path, normalized-snippet hash), so a
  rescan with it on never churns a finding.
- **Uncovered languages:** `SastLanguageCoverage` (three buckets covering every `lang_detect` name). Reported:
  Groovy, Rust, C, C++, Swift, PowerShell, **Vue, Svelte**. **Vue/Svelte measured** — Opengrep 1.31.0 targets
  `.vue`/`.svelte` (they appear in `paths.scanned`, 182 rules applied) but produces **zero** findings even for a
  top-level `eval()`/`document.write()` that fires three JS rules in a `.js` file.
- **Skipped files close nothing (domain rule 3 at file granularity).** `run-scan.sh` runs with
  `--timeout 60 --timeout-threshold 3` (default 5 s dropped a slow rule's matches on large files). Any file
  Opengrep reports in `errors[]` **or** in `paths.skipped` with a size/read/parse reason
  (`exceeded_size_limit`, `insufficient_permissions`, `analysis_failed_parser_or_internal_error`; `--verbose`
  makes it emit `paths.skipped`) is carried to the worker (paths + error-type only, D-053/S1) and its open SAST
  findings are **frozen** at reconcile — never false-solved. A `SAST_FILES_SKIPPED` warning (count + types + up to
  10 paths) shows in the coverage banner. Design skips (gitignore, `wrong_language`, our `EXCLUDED_PATH`) are not
  frozen.

## ib-api scan-time budget + the 70 → 88 timeout fix

Real Celloscope repo `ib-api` (`807b6aa`, 2594 Java files), scanned **read-only** (file:// clone of HEAD, never
built/run/committed):

| | value |
|---|---|
| SAST before (4 packs + aikido + custom, no excl/taint) | 119 s, 78 findings |
| SAST after (production: 10 packs + 142 excludes + taint, **`--timeout 5`**) | 194–203 s, **70** findings, **2 Timeout-skipped files** |
| SAST after (production, **`--timeout 60`**) | 196 s, **88** findings, **0 skipped** |
| Full scan after (`--timeout 60`) | ~260 s (SCA 54 s, SAST ~196 s, rest <5 s) |

The 70 → 88 jump is the timeout fix: at the 5 s default, `java…formatted-sql-string` timed out on 1–2 large
`src/test` files and silently dropped its matches; `--timeout 60` clears every file (0 skipped) with ample margin
under the 30-min container timeout. **Determinism:** two production scans of ib-api produced an **identical**
`(check_id, file, fingerprint)` set (88 each, 0 diff). Budget stop-rule not triggered → proceeded.

### D-061 duplicate-rule map extension (from real output)

On the Flask app plexicus, one bug fired several rules (e.g. the SQLi → django+flask `tainted-sql-string`,
`lang.formatted-sql-query`, `sqlalchemy-execute-raw-query`; `raw-html-format` fired 4× django + 4× flask).
Captured from real production scans of plexicus (Flask) and PyGoat `2aa4cc14` (Django), three
winner/loser pairs were added — **same-line checked empirically on plexicus + PyGoat; runtime matches per
file** (framework/library-specific rule wins):

| loser → Ignored | winner (stays open) | same-line check (empirical) |
|---|---|---|
| `django…tainted-sql-string` | `flask…tainted-sql-string` | plexicus `app.py:51`; pygoat `sql_injection_lab/app.py:50` |
| `lang…formatted-sql-query` | `sqlalchemy…sqlalchemy-execute-raw-query` | plexicus `app.py:52`; pygoat `…app.py:57` |
| `django…raw-html-format` | `flask…raw-html-format` | plexicus `app.py:61/67/79/116` |

**Safety — empirical, not enforced:** same-line checked empirically on plexicus + PyGoat; runtime matches per
file. D-061 ignores a loser whenever its winner fires anywhere in the same file, so on another repo a loser-only
line in such a file would be hidden; the check only shows that on these two repos every ignored loser hit had the
winner on the same line. Two candidates were **dropped** by this check: `avoid-pickle →
flask.insecure-deserialization` (would hide a distinct pickle bug at pygoat `software_integrity_lab/app.py:19`,
loser with no same-line winner) and `django…sql-injection-db-cursor-execute` (fires alone on plexicus
`app.py:49`, no same-line winner). Effect on a plexicus rescan: **6 SAST findings move to Ignored
(`DUPLICATE_RULE`)** — 1 high (django tainted-sql-string) + 5 medium — so **72→66 open / 14→13 high**; the kept
winners stay open, and `avoid-pickle` + `sql-injection-db-cursor-execute` correctly stay open.
