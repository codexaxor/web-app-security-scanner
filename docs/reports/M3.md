# Milestone report: M3 Issue model

Branch: `feature/m3-issue-model` · Commit: `50af121` · Date: 2026-10-14 · Model(s) used: Claude Opus 4.8

M3 turns M2's interim `scan_finding` rows into the deduplicated, lifecycle-tracked issue model: `issue_group` /
`sub_issue` with stable fingerprints, `reconcile` (open / solved / reopened) honouring per-scanner success,
`triage_event` for every status change, a persistent `repository_event` audit trail for D-020's connection
lifecycle, and a read-only issue API. Severity/scoring stays out (store the tool severity; scoring is M5); no UI
(M8). M2's only scanner is secrets, so the lifecycle is exercised on secret findings, but the fingerprint and
reconcile logic is type-agnostic and unit-tested for all five types.

## What was built

- `core/.../reconcile/Fingerprints.java` — per-type SHA-256 fingerprints (SCA/SAST/secret/IaC/EOL) and group
  keys; normalizes paths (forward slashes, strip leading `./`, keep case) before hashing; never the line number.
- `core/.../reconcile/Reconciler.java` — pure decision engine: new-open / reopened / seen / solved. Solves only
  findings whose scanner succeeded; a failed/absent scanner closes nothing; `ignored` stays ignored (seen or
  missing), no event; reopen is suppressible per scanner (changed secret key).
- `core/.../crypto/SecretFingerprinter.java` — added `keyId()` (first 8 hex of `HMAC(key, "secscan-key-id")`).
- `app/.../issue/` — `IssueGroup`, `SubIssue`, `TriageEvent` entities + repositories; `ReconcileService`
  (loads entities, delegates to the core `Reconciler`, writes `triage_event`s, recomputes group status; runs in
  the SAME transaction as `recordSuccess`, idempotent, stale-guarded, with the D-029 secret-key guard);
  `IssueService` + `IssueController` (read-only API); `IssueGroupView`/`SubIssueView` DTOs (preview only).
- `app/.../repository/` — `RepositoryEvent` entity + repository + `RepositoryEventRecorder`, wired into
  connection removal (`GitLabConnectionService.delete`) and the connection guard (confirm/deactivate).
- `app/.../scan/worker/ScanStateService.java` — calls `reconcile.reconcile(scanId)` inside `recordSuccess`.
- `app/.../scan/worker/ScannerEnvironmentCheck.java` — reports NOT ready without a configured fingerprint key.
- `app/.../scan/Scan.java`, `ScanRepository.java` — `reconciledAt` + `markReconciled()` + the stale-guard query.
- `app/.../scan/parse/ScannerOutputParser.java` — clamps any preview > 4 chars / with whitespace to `****`.
- `scanner-image/secscan-lib.sh` — `secret_preview` operates on the whole secret (not line-by-line).

## Migrations

**`V8__issue_model.sql`** — in full:

```sql
-- M3: the deduplicated issue model. M2 stored raw scan_finding rows per scan (D-024); reconcile turns those
-- into issue_group (what users triage) and sub_issue (one concrete finding with a stable fingerprint), tracking
-- the open/solved/reopened lifecycle and writing a triage_event for every status change (CLAUDE.md domain rules
-- 2-4, SPEC "Issue lifecycle"). Scoring columns (cvss/cwe/epss/score/...) are added by M5's own migration;
-- migrations are immutable once applied, so new behaviour is always a new migration (V8+), never an edit.
--
-- Every business table carries workspace_id and every query filters by it (domain rule 1).

-- Atomicity + stale guard (M3 plan additions 1 & 2): findings are stored and reconciled in one transaction,
-- which stamps reconciled_at. Reconcile also skips a scan when a newer scan of the same repository has already
-- been reconciled (out-of-order completion must not let an older view re-open/re-solve findings).
alter table scan add column reconciled_at timestamptz;

-- A Feed row: the group users triage. status/severity are derived from its sub-issues (M3 derives status;
-- severity_score and fix_time_minutes are populated by M5). group_key is "type|discriminator" (Fingerprints).
create table issue_group (
    id               uuid        primary key,
    workspace_id     uuid        not null references workspace (id),
    repository_id    uuid        not null references repository (id),
    type             text        not null check (type in ('sca', 'sast', 'secret', 'iac', 'eol')),
    group_key        text        not null,
    title            text        not null,
    subtitle         text,
    status           text        not null default 'open'
                       check (status in ('open', 'solved', 'ignored')),
    severity_score   int,
    fix_time_minutes int,
    first_seen_at    timestamptz not null default now(),
    created_at       timestamptz not null default now(),
    constraint uq_issue_group_key unique (workspace_id, repository_id, group_key)
);

create index idx_issue_group_workspace on issue_group (workspace_id);
create index idx_issue_group_repository on issue_group (repository_id);

-- One concrete finding. Its identity is fingerprint (SHA-256 of the type's fields, never the line number),
-- unique per repository. scanner records which scanner produced it so reconcile can honour per-scanner success
-- (a failed scanner never closes its findings). secret_hash is the keyed HMAC (D-027) and key_id the short
-- fingerprint-key id (D-029); neither is ever returned by the API. line is informational only.
create table sub_issue (
    id                 uuid        primary key,
    workspace_id       uuid        not null references workspace (id),
    group_id           uuid        not null references issue_group (id) on delete cascade,
    repository_id      uuid        not null references repository (id),
    type               text        not null check (type in ('sca', 'sast', 'secret', 'iac', 'eol')),
    scanner            text        not null,
    fingerprint        text        not null,
    vuln_id            text,
    rule_id            text,
    package            text,
    installed_version  text,
    fixed_version      text,
    file_path          text,
    line               int,
    snippet_hash       text,
    secret_hash        text,
    secret_preview     text,
    key_id             text,
    tool_severity      text,
    status             text        not null default 'open'
                         check (status in ('open', 'ignored', 'solved')),
    ignore_reason      text,
    first_seen_scan_id uuid        references scan (id),
    last_seen_scan_id  uuid        references scan (id),
    solved_at          timestamptz,
    created_at         timestamptz not null default now(),
    constraint uq_sub_issue_fingerprint unique (workspace_id, repository_id, fingerprint)
);

create index idx_sub_issue_workspace on sub_issue (workspace_id);
create index idx_sub_issue_group on sub_issue (group_id);
create index idx_sub_issue_repository on sub_issue (repository_id);

-- The audit trail: one row per status change (domain rule 4), actor system or user, with the reason code and
-- the scan that caused it. Either sub_issue_id or group_id identifies the subject (both nullable so the table
-- can hold group-level events later).
create table triage_event (
    id           uuid        primary key,
    workspace_id uuid        not null references workspace (id),
    sub_issue_id uuid        references sub_issue (id) on delete cascade,
    group_id     uuid        references issue_group (id) on delete cascade,
    from_status  text,
    to_status    text,
    actor        text        not null check (actor in ('system', 'user')),
    reason_code  text,
    scan_id      uuid        references scan (id),
    at           timestamptz not null default now()
);

create index idx_triage_event_workspace on triage_event (workspace_id);
create index idx_triage_event_sub_issue on triage_event (sub_issue_id);
create index idx_triage_event_group on triage_event (group_id);

-- D-028: a dedicated table for repository lifecycle events (connection reassignment/deactivation on removal,
-- D-020), kept separate from triage_event (which is specifically the issue-status audit trail). from/to
-- connection ids are plain uuids, not FKs: the "from" connection is typically deleted at the moment the event
-- is written.
create table repository_event (
    id                 uuid        primary key,
    workspace_id       uuid        not null references workspace (id),
    repository_id      uuid        not null references repository (id),
    event_type         text        not null
                         check (event_type in ('REASSIGNED', 'DETACHED', 'DEACTIVATED', 'CONFIRMED',
                                               'REATTACHED')),
    from_connection_id uuid,
    to_connection_id   uuid,
    reason_code        text,
    detail             text,
    at                 timestamptz not null default now()
);

create index idx_repository_event_workspace on repository_event (workspace_id);
create index idx_repository_event_repository on repository_event (repository_id);
```

**`V9__scrub_leaky_secret_previews.sql`** — in full:

```sql
-- M3 manual-check fix: a line-oriented preview step (cut -c1-4 in scanner-image/secscan-lib.sh) emitted the
-- first 4 characters of EVERY line of a multi-line secret (e.g. a PEM private key), leaking a fragment of each
-- line into secret_preview. The scanner now previews the whole secret as one string (<= 4 chars, no newline),
-- and the worker clamps anyway. This migration scrubs any rows already written by the old code: a valid preview
-- is at most 4 characters and single-line, so anything longer or containing a CR/LF is replaced with the
-- fully-masked '****'. (V8 is already applied and must not be edited — CLAUDE.md.)

update sub_issue
   set secret_preview = '****'
 where secret_preview is not null
   and (char_length(secret_preview) > 4
        or secret_preview like E'%\n%'
        or secret_preview like E'%\r%');

update scan_finding
   set secret_preview = '****'
 where secret_preview is not null
   and (char_length(secret_preview) > 4
        or secret_preview like E'%\n%'
        or secret_preview like E'%\r%');
```

## API changes

All under `/api/v1`, HTTP Basic (D-010), server-side pagination. Read-only (triage actions are M7).

| Method | Path | Behavior |
| --- | --- | --- |
| GET | `/issue-groups?repositoryId=&type=&status=&page=&size=` | `PagedResponse<IssueGroupView>`, workspace-scoped, filters optional; ordered newest-first by first-seen (severity order arrives with M5) |
| GET | `/issue-groups/{groupId}/sub-issues?page=&size=` | `PagedResponse<SubIssueView>` (404 if the group is not in this workspace) |

`SubIssueView` exposes the masked `secretPreview` only — never `secret_hash`, `key_id`, the fingerprint or the
snippet hash (asserted by `IssueApiIT` and `SecretPreviewLeakIT`).

## Deviations from SPEC.md

- **`repository_event` is a new table** not in the spec's data model (D-028); it persists D-020's connection
  lifecycle, which the spec's `triage_event` could only hold awkwardly (null sub-issue/status).
- **`sub_issue` carries `repository_id`** (the spec lists only `group_id`) and `scanner`/`key_id`, and
  `issue_group`/`sub_issue` carry `workspace_id` (domain rule 1). `scanner` lets reconcile key off per-scanner
  success; `repository_id` makes the per-repo unique index and reconcile queries direct (consistent with M2's
  `scan_finding`).
- **Scoring columns deferred to M5**: `cvss`, `cwe`, `epss`, `in_kev`, `score`, `score_breakdown`, and
  `issue_group.severity_score`/`fix_time_minutes` are not populated (the brief: store tool severity, no scoring).
  They are added by M5's migration.
- **`scan.reconciled_at`** added for one-transaction atomicity + the stale guard (plan addition 1/2).
- **`first_seen_scan_id`/`last_seen_scan_id` on `sub_issue` are unindexed** (scan-reference FKs not queried by
  in M3); the identity index `(workspace_id, repository_id, fingerprint)` and the group/repo FKs are indexed.
- Backend only; no UI (M8). Only secret findings are produced (M2's only scanner), though reconcile and
  fingerprints are type-agnostic and unit-tested for all five types.

## Decisions made (also in DECISIONS.md)

- **D-028** repository lifecycle events in a dedicated `repository_event` table, not `triage_event`.
- **D-029** store a short `key_id` per secret sub-issue; a changed `SECSCAN_FINGERPRINT_KEY` logs an error and
  does not solve/reopen secrets that scan; the key must never change once secrets are stored.

## Fixed during manual check

**`secret_preview` leaked multi-line secrets (BLOCKER).** A PEM private key (gitleaks rule `private-key`)
produced `secret_preview = "----\nMIIE\nX3N1\n…"` — the first 4 characters of every PEM line (~28 fragments) —
because the container's sanitize step used line-oriented `cut -c1-4`. Fixed end to end:

1. **scanner-image** (`secscan-lib.sh`): `secret_preview` now takes the first 4 characters of the **whole**
   secret via shell parameter expansion (not line-by-line) and strips any CR/LF — the preview is always ≤ 4
   characters and single-line. The hash was already over the full secret (`printf '%s' "$secret" | sha256sum`);
   confirmed, unchanged.
2. **Java defense in depth** (`ScannerOutputParser.safePreview`): any preview longer than 4 chars or containing
   whitespace is clamped to `****` with a warning that never includes the value.
3. **V9 migration**: scrubbed existing `sub_issue`/`scan_finding` rows with a leaky preview to `****`.
4. **Tests**: `SecretPreviewLeakIT` runs the real container over an RSA key generated at test time (never
   committed), asserting preview ≤ 4 chars / no newline, the hash is over the whole secret (not one line), and
   no key fragment reaches the preview, hash, log excerpt or the API; plus multi-line cases in
   `MaskPreviewScriptTest` (real shell), a `safePreview` unit test, and a V9 scrub-predicate test.
5. **Build**: `buildScannerImage` now stamps a `scanner-image/` content hash as an image label and rebuilds on a
   mismatch, so an edit to `scanner-image/` can no longer leave a stale image behind.

## Review follow-ups (2026-10-15)

A fresh-session review of `develop...HEAD` found no blockers; it passed the checklist and confirmed the
one-transaction reconcile, the stale guard (safe because `uq_scan_active_per_repository` serialises a repo's
scans), the failed/absent-scanner rule, and the end-to-end secret-preview fix. Addressed before finishing:

- **Domain rule 1 on four internal queries (should-fix).** Four lookups keyed only by a workspace-unique UUID
  now also filter by `workspace_id`, so every query satisfies rule 1 literally (no behaviour change, all keys
  were already workspace-unique): `ScanRepository` stale guard
  (`existsByWorkspaceIdAndRepositoryIdAndReconciledAtIsNotNullAndCreatedAtGreaterThan`),
  `SubIssueRepository.findByWorkspaceIdAndGroupId` (was `findByGroupId`), `ReconcileService` group recompute
  (`groups.findByIdAndWorkspaceId`), and `TriageEventRepository.findByWorkspaceIdAndSubIssueIdOrderByAtAsc`.
- **D-029 refined from scanner-level to row-level (should-fix).** A changed `SECSCAN_FINGERPRINT_KEY` no longer
  freezes the whole secret scanner. Reconcile now partitions secret sub-issues by `key_id`: current-key rows
  reconcile normally (solve/reopen); rows under a superseded key id are frozen (never solved/reopened, no
  event). The single error log names only the count and the stale key id(s). Operators clean up old-key rows
  manually (bulk ignore is M7). New tests: `ReconcilerTest.aFrozenFingerprintIsNeverSolvedReopenedOrSeen` and
  `afterAKeyChangeCurrentKeyRowsReconcileWhileFrozenRowsStayUntouched`;
  `ReconcileServiceIT.afterAKeyChangeCurrentKeySecretsSolveAndReopenWhileOldKeyRowsAreFrozen` (a new-key secret
  is solved and another reopened while an old-key row stays untouched with no event). See updated D-029.
- **`secret_preview` is `****` for secrets shorter than 12 chars (intended, from M2).** This is deliberate — a
  4-char preview of a short credential reveals too large a fraction — and is recorded in D-027. Noted here so
  it is not mistaken for drift from the "first 4 chars" phrasing of the domain rule.
- **`triage_event` cascade / composite-FK (nit, deferred to M10).** `ON DELETE CASCADE` on the audit FKs and
  the single-column FKs (no DB-enforced cross-row `workspace_id` consistency) are accepted for M3 — nothing
  deletes issue rows and the deployment is single-workspace — and are left unchanged. A note in D-028 records
  the revisit (before hard deletes or multi-tenant).
